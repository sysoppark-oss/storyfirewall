# 검증 의뢰서 43차 — 파괴 행위 자동 대응 · 긴급 차단 · 서비스 SID 조건 · PID 재사용 · HUD (2026-11-08)

대상: Story Firewall 제품 A(Windows 10 22H2·11 x64 개인 방화벽, 사용자 모드 WFP + ETW, 커널 드라이버 없음).
코드: 공개 저장소 sysoppark-oss/storyfirewall (커밋 d6d4e27 ~ 13a7598). 설계 기준: 대시보드 개편안 3판 1-1(긴급 차단)·4-1(HUD)·4-2(자동 대응).
지난 41·42차에서 정한 것(서명자 예외, 묻지 않기, 되돌리기, RDP 복합 조건, 세 축 반복 승격)을 구현했고, 러너(일회용 VM)와 실제 노트북에서 돌려 본 뒤
규칙을 좁혔다. 이번에는 **"이 설계가 깨지는 입력·순서"**를 먼저 묻는다.

## 0. 답변 형식
- 질문 번호(Q1~Q6)로 답하고, 각 질문마다 **먼저 깨는 시나리오**(공격자 또는 정상 프로그램이 어떤 입력·순서로 오탐·미탐·잠김을 만드는지)를 적고,
  그다음 **고칠 방법**을 적을 것. 시나리오에는 전제(관리자 권한 필요 여부, 사용자 클릭 필요 여부)를 붙일 것.
- "맞다/틀리다" 확인만 하는 답은 필요 없다. 깨는 방법이 없으면 "찾지 못함"이라고 쓰고 그렇게 본 근거를 쓸 것.
- Windows API·WFP 동작은 Microsoft 문서 근거를 달고, 문서로 확인하지 못한 것은 "추측"이라고 쓸 것.

## 1. 구현한 것 (요약)

### 1-1. 파괴 행위 자동 대응 (3판 4-2, 기본 켬)
- 계기: 사건 안 어떤 프로세스가 T1490 명령을 실행한 `ran` 선(vssadmin delete shadows · wmic shadowcopy delete · bcdedit recoveryenabled no ·
  wbadmin delete catalog …). ETW Kernel-Process 시작 이벤트의 명령줄로 판정.
- 원인 프로그램 고르기: 명령을 실행한 프로세스에서 부모로 올라가며 **경로에 `\windows\`가 들어간 실행 파일은 건너뛰고**, 처음 만나는
  Windows 밖 조상 **하나만** 본다(그 위로 오르지 않음). 최대 64단계.
  - 그 조상이 Microsoft 서명 → 대응 안 함(인시던트로만).
  - 유효 서명이고 서명자 이름이 사용자 허용 목록 항목으로 **시작**하면(대소문자 무시) → 대응 안 함.
  - 서명 없음·깨짐·불신·Microsoft 아닌 유효 서명 → **Full**: 그 프로그램부터 끊기(그 프로세스·자손 종료 + 경로 WFP 차단 + 자리잡기 제거).
  - 서명을 아직 모름(서비스보다 먼저 켜진 프로세스) 또는 Windows 밖 조상이 없음 → **ChildOnly**: 명령을 실행한 프로세스만 종료.
- 묻지 않고 바로 정책을 확정하고, 인시던트 카드에 `auto:<정책id>:<판>` 표시와 [되돌리기](정책 제거)를 둔다.
- 좁힌 이유(A29 러너 실측): 처음에는 사슬 맨 위까지 올라가 ① 서명 사실이 없는 러너 에이전트(Runner.Listener) 트리를 죽였고
  ② 사슬 중간의 msedge.exe(Microsoft 서명)가 면제를 줘 Edge에서 바로 실행한 시험 악성 프로그램이 빠져나갔다.
- 한계: ETW는 사후 통지라 "피해 줄이기"이지 "막기"가 아니다(vssadmin 은 수백 ms 안에 끝날 수 있음).

### 1-2. 긴급 차단 (3판 1-1, 9단계)
- 전용 Sublayer `{5f1a2b3c-4d5e-4f60-8172-839405a6b7cb}`(weight 0x8001), **비영구** 필터 — 재부팅하면 풀린다(PC가 갇히지 않는 안전판).
- 안: 전체 차단(나가는·들어오는, v4·v6, weight 1) + 예외 허용(더 높은 weight):
  루프백 / svchost.exe↔53(Dnscache 서비스 SID 조건, SID 유형이 Unrestricted·Restricted일 때만) / DHCP 67·547 나가기·68·546 들어오기(Dhcp 서비스 SID 조건, 같음) /
  이 앱 실행 파일(있는 것만) / 사용자가 고른 원격 도구 경로(있어야 하고 `\Windows\` 아래 아님, 최대 8개, 지금 통신 중인 원격 도구를 미리 채움) /
  RDP: 지금 접속한 세션의 상대 IP → svchost.exe 로컬 3389.
- 승인(UAC) 뒤 60초 안에 [유지]를 누르지 않으면 자동 되돌림. 기한(기본 30분) 만료 시 해제. 재부팅 뒤에는 서비스가 정책을 "만료"로 닫고 다시 걸지 않는다.
- 노트북 실측: 848건 차단, claude.exe 예외로 원격 세션 유지, 해제 정상. A30 러너 시험 통과(DNS·HTTPS 예외 경로 확인).

### 1-3. 서비스 SID 조건
- 서비스 SID = S-1-5-80 + SHA-1(서비스 이름 대문자 UTF-16LE). 조건 FWPM_CONDITION_ALE_USER_ID, SD `O:SYG:SYD:(A;;CCRC;;;<SID>)`.
- QueryServiceConfig2W(SERVICE_CONFIG_SERVICE_SID_INFO) 유형이 1(Unrestricted)·3(Restricted)일 때만 건다. 아니면 svchost 경로 조건만.

### 1-4. 출처 그래프 PID 재사용 수정
- 노드 시각(first_ts)이 이번 부팅 시각보다 2분(BOOT_SLACK) 넘게 이르면 이전 부팅의 프로세스로 보고, 이번 부팅 이벤트의 부모·주인으로 쓰지 않는다.
  (재부팅 뒤 같은 PID 가 이전 부팅 노드에 붙어 엉뚱한 사슬이 생기던 결함. 이미 생긴 잘못된 선은 아직 남아 있음.)

### 1-5. HUD (3판 4-1)
- ② 트레이 아이콘: 20초마다 서비스에 `story.events(level_min=suspicious, triage=open)`·`emergency.status`를 물어 점 색(심각 진한 빨강·높음 빨강·없음 초록·끊김 회색)과 툴팁.
- ① 작은 상시 창(선택): 항상 위, 서비스에 붙지 않고 UI 프로세스가 보내는 `hud-state` 이벤트만 그림. 누르면 본 창, 끌면 이동.
- 실기기에서 고친 결함 3건: 동기 명령 안 창 생성 → WebView2 교착(빈 창), 본 창과 다른 `additionalBrowserArgs` → 0x8007139F, RPC 응답 봉투 미해제 → 늘 0건.

### 1-6. (7단계) 반복 승격
- 낮은 수준 사건이 출처·접속지·통신 양식 중 어느 축으로든 7일 3건이면 중간으로 승격(42차 Q4 그대로).

## 2. 질문

**Q1 (자동 대응 — 원인 프로그램 고르기를 깨기)**
① `\windows\` 부분 문자열로 "Windows 도구"를 판정한다. 일반 사용자 권한으로 쓸 수 있는 `C:\Windows\Temp`, `C:\Windows\Tasks`, `C:\Windows\tracing` 같은 곳,
   또는 `D:\backup\windows\x.exe`처럼 경로 중간에 windows 가 들어간 곳에 악성 프로그램을 두면 건너뛰어진다. 그러면 원인이 위쪽 정상 프로그램(예: explorer 바로 아래면 "조상 없음" → ChildOnly)으로
   바뀌어 Full 대응을 피한다. 이 우회의 현실성과, 판정 기준(%SystemRoot% 정확 접두 + 쓰기 가능 하위 폴더 제외 + Microsoft 서명 확인 중 무엇)을 제안해 달라.
② 허용 목록이 서명자 이름 **앞부분 일치**다. "Acme"를 허용하면 "Acme Evil Ltd"도 통과한다. 정확 일치·인증서 지문·발급자 사슬 중 개인용 제품에 맞는 것은?
③ 공격자가 정상 Microsoft 서명 프로그램을 부모로 만드는 방법(예: rundll32·mshta·msiexec·WMI(WmiPrvSE)·작업 스케줄러(svchost)·COM 서버를 거쳐 vssadmin 실행)은 모두 `\windows\` 아래라 건너뛰고 조상이 없어 ChildOnly가 된다.
   즉 **LOLBin 경유 파괴는 원인 프로그램을 끊지 못한다**. ETW만으로(커널 드라이버 없이) 이 경우의 원인을 이어 붙일 방법이 있는가(WMI 활동 ETW, TaskScheduler 로그, 부모 PID 위조 탐지 등)?
④ 부모 PID 위조(PROC_THREAD_ATTRIBUTE_PARENT_PROCESS)로 악성 프로그램이 vssadmin 의 부모를 explorer 로 꾸미면? Kernel-Process ETW 의 ParentProcessID 는 위조된 값인가, 실제 생성자인가(문서 근거)?
⑤ "서명을 아직 모름 → ChildOnly"를 노려 서비스보다 먼저 켜지는(자리잡기된) 악성 프로그램은 영원히 Full 대응을 받지 않는가? 서비스 시작 뒤 이미 실행 중인 프로세스의 서명을 비동기로 채우는 것의 비용·위험.
⑥ 반대로 **오탐 종료**: Microsoft 아닌 유효 서명 백업·디스크 관리 도구(예: 서드파티 백업, 게임 런처의 시스템 복원 정리)가 vssadmin 을 부르면 Full 로 끊긴다. 사용자가 허용 목록을 미리 넣지 않은 상태의 피해를 줄일 방법(첫 대응은 ChildOnly 로만? 유명 서명자 기본 목록?)

**Q2 (긴급 차단 — 잠김·우회)**
① WFP 중재: 전용 Sublayer 안에서 전체 차단(weight 1) < 예외 허용. 다른 Sublayer(Windows 방화벽·다른 보안 제품)의 **hard permit**(FWPS_RIGHT_ACTION_WRITE 지움) 또는 더 높은 우선순위 필터가
   우리 차단을 무효로 만드는 경우가 있는가? 반대로 우리 예외 허용이 다른 Sublayer 의 차단에 막혀 원격 세션이 끊길 수 있는가(문서 근거)?
② 예외가 **경로 기반**(원격 도구·이 앱)이다. 이미 코드 실행을 얻은 공격자가 예외 프로세스에 주입(CreateRemoteThread·APC)하거나, 예외 도구(TeamViewer 등)를 자기 C2 로 쓰면 긴급 차단을 뚫는다.
   이 한계를 승인 창에 어떻게 적어야 하며, 줄일 방법이 있는가(예: 원격 도구 예외에 원격 IP·포트까지 고정)?
③ svchost.exe↔53 예외: 서비스 SID 유형이 맞지 않는 PC에서는 **모든 svchost 서비스**가 53으로 나간다. DNS 터널링이 이 틈으로 가능한가? Dnscache 외 경로로 53을 쓰는 정상 서비스가 있어 SID 조건이 오히려 DNS 를 끊는 경우는?
④ 비영구 필터 + 재부팅 해제: 공격자가 재부팅을 유도(또는 사용자가 재부팅)하면 차단이 풀린다. 서비스는 재부팅 뒤 다시 걸지 않는다 — 이 선택(갇힘 방지 > 차단 유지)이 맞는가? 자동 재적용 조건을 둔다면?
⑤ 60초 [유지] 확인: UI 가 멈추거나 엔진이 바쁘면(실측 [유지] 응답 약 20초) 의도와 달리 되돌려질 수 있다. 반대로 원격으로 접속한 사용자가 예외를 잘못 골라 자기 세션을 끊으면 60초 뒤 되돌림이 유일한 복구 수단이다. 이 두 실패의 균형.
⑥ IPv6: 루프백 ::1·DHCPv6 외에 NDP(ICMPv6 RA/NS/NA)를 막으면 IPv6 연결이 깨진다. 긴급 차단 해제 뒤 IPv6 가 곧바로 회복되는가, 아니면 RA 주기만큼 끊겨 있는가(추측이면 추측)?

**Q3 (서비스 SID 조건)**
① SID 유형 판단은 차단 시점 한 번이다. 이후 `sc sidtype`으로 유형이 바뀌면(관리자 필요) 예외가 어긋난다 — 위험한가?
② 서비스가 사용자로 가장(impersonate)해 소켓을 열 때 ALE_USER_ID 가 서비스 SID 를 포함하지 않는 경우(Microsoft 포럼 답만 확인). Dnscache·Dhcp 가 그러는 경우가 문서로 있는가?
③ 서비스 SID 를 직접 계산(SHA-1)한다. LookupAccountNameW("NT SERVICE\\Dnscache")로 얻는 것과 다를 수 있는 경우가 있는가?

**Q4 (PID 재사용 수정)**
① 기준이 "노드 시각 < 부팅 시각 − 2분"이다. 부팅 직후 시계 보정(NTP·RTC 틀림)으로 시각이 크게 움직이면 이번 부팅 노드가 이전 부팅으로 잘못 분류되거나 그 반대가 되는 순서를 적어 달라.
② 절전·최대 절전(Fast Startup 포함)은 "부팅"이 아니다. Fast Startup 재개 때 부팅 시각(GetTickCount64 기반?)과 PID 공간이 어떻게 되는지 — 우리 판정이 깨지는가?
③ 이미 생긴 잘못된 선 정리: 근거 원시 이벤트가 7일 보관이라 재계산할 수 있다. 지울 것인가, "불확실" 표시만 할 것인가.

**Q5 (HUD)**
① HUD 창은 서비스에 붙지 않고 UI 프로세스의 이벤트만 그린다. 같은 사용자 권한의 다른 프로그램이 HUD 창에 가짜 상태를 그리거나(창 메시지·접근성 API) "보호 중" 상태를 위조해 보일 방법이 있는가? 위험도.
② 사건 제목(파일 이름 포함)을 HUD 와 트레이 툴팁에 그대로 넣는다. 공격자가 고른 파일 이름(예: `보호 중 · 미조치 없음.exe`, 오른쪽→왼쪽 표시 문자 U+202E)으로 상태를 속일 수 있는가? 지금은 제어 문자만 걸러 낸다.
③ 20초 주기 질의(story.events limit 200)가 사건이 많은 PC 에서 엔진 잠금을 잡아 다른 작업을 늦출 위험. 별도 가벼운 요약 RPC(카운터만)를 둘 것인가.

**Q6 (7단계 반복 승격)**
① 세 축 OR 승격(7일 3건)을 정상 프로그램이 일상적으로 만족해 "중간" 알림이 쏟아지는 대표 사례(자동 업데이트·CDN·브라우저)를 적고, 축별로 제외 규칙을 제안해 달라.

## 3. 우리가 이미 의심하는 점 (먼저 깨 보기를 바라는 곳)
- Q1-①의 `\windows\` 부분 문자열 판정과 Q1-②의 앞부분 일치 — 코드를 보면 바로 보이는 약점이다. 고칠 방향을 정하기 전에 현실성 평가가 필요하다.
- Q1-③ LOLBin 경유: 지금 구조에서 가장 큰 미탐으로 본다.
- Q2-② 예외 프로세스 주입: 긴급 차단의 근본 한계로 본다(드라이버 없이 막을 수 없다고 추측).

## 4. 묻지 않는 것
- 코드 서명 인증서(사지 않기로 함), 용어·화면 디자인(40~42차), 점수 경계값(39차).
