# 답변반영 57차 — Claude 가 못 본 것: 보고서 만든 기록·진단 호출·판정 뷰 (2026-11-22)

의뢰서: 검증의뢰서_57차_Claude가못본것_2026-11-21.md. 코드 원문을 부록으로 붙인 첫 의뢰다. Gemini 가 부록의 줄 번호를 근거로 답해 지적마다 바로 대조할 수 있었다(55·56차와 달리 "코드가 이럴 것이다" 식의 추측이 거의 없다).

| 번호 | Gemini 지적 | 판단 | 근거·조치 |
|---|---|---|---|
| Q1-a | Windows 에서는 대상 파일을 다른 프로그램(백신 검사·미리 보기)이 잡고 있으면 이름 바꾸기가 거부된다 → 그 한 줄을 잃는다 | **수용** | Linux 시험으로는 볼 수 없던 것. `append` 가 `PermissionDenied` 면 40ms 간격으로 3번 더 해 본다(`RENAME_TRIES`). 그래도 안 되면 한 줄을 잃고 끝(저장은 막지 않는다 — 2.3). |
| Q1-b | 화면 프로그램이 두 개 뜨면 프로세스 사이 잠금이 없어 줄이 사라진다 | **반박(조치 없음)** | 화면은 한 개만 뜬다(`tauri-plugin-single-instance` — 두 번째 실행은 기존 창을 띄우고 끝난다, `ui/src-tauri/src/lib.rs`). 부록에 없던 코드라 Gemini 는 볼 수 없었다. |
| Q2 | `%LOCALAPPDATA%` 가 네트워크·장치 경로이거나, 그 아래 폴더가 접합이면 뜻하지 않은 곳에 쓴다. 관리자 권한으로 띄우면 보호된 폴더에 쓰게 된다 | **수용(방법은 다르게)** | 드라이브 글자로 시작하는 로컬 경로만 받고(`made_log::is_plain_local_path`, 시험), `StoryFirewall` 폴더나 기록 파일이 재분석 지점(접합·심볼릭 링크)이면 기록하지 않는다(`report.rs` `is_link`). `SHGetKnownFolderPath` 로 바꾸지는 않았다 — 환경 변수를 바꿀 수 있는 쪽은 이미 같은 사용자이고, 권한을 넘는 길은 접합이라 그쪽을 막는 편이 맞다. 확인과 쓰기 사이의 바꿔치기는 남는다(편의 기록이라 여기까지). |
| Q3 | 논리 프로세서 256개 넘으면 버퍼 부족. 큰 버퍼는 성공. 서비스·powrprof 문제 없음 | **기록만** | 256개 넘는 PC 에서는 그 값만 빠진다(진단). "버퍼가 커도 성공"은 우리가 확신하지 못하던 점 — 노트북 실측(클럭 2039/2100 이 찍힘)과도 맞는다. |
| Q4 | 코어 목록이 바뀌면(핫 애드·VM 이주) `find` 가 `None` — 틀린 등급은 아니고 그 값만 빠진다. 그룹이 여럿이어도 전부 온다 | **기록만** | 개인 PC 대상이고 진단 값이다. 틀린 값을 내지 않는다는 확인으로 충분. |
| Q5 | `GetThreadTimes` 는 시계 인터럽트(15.6ms) 단위로만 오른다 — "커널 93ms" 같은 한 번의 값은 믿지 말고 평균으로 | **수용(해석)** | 코드 변경 없음. 93ms = 15.625 × 6 으로 정확히 맞아떨어진다. 앞으로 커널 시간은 평균으로만 말한다. (공식 문서에 명시된 문장인지는 확인하지 못했다 — 값의 모양이 뒷받침한다.) |
| Q6 | 낯선 관계 이름 200개로 이름 칸을 다 채우면 진짜 이름이 "기타"로 뭉개진다. `label` 은 거르지 않는다 | **반박** | 관계 이름은 수집기가 `Rel` 열거형으로만 쓴다(12가지). DB 를 고칠 수 있으면 관리자다. `label` 은 호출부의 고정 글자 다섯 개다. |
| Q7-1 | 죽은 칸이 글자 버퍼(관계 이름·속성)를 쥔 채 30분 남는다 — 선이 자주 바뀌면 수백 MiB | **수용** | `remove_edge` 가 죽은 칸의 `rel`·`attrs_json` 을 비운다. 죽은 칸 수를 진단에 낸다(`MemStats.dead_slots`, "선 목록의 죽은 칸"). 칸 자체(112 B)는 다음 전체 다시 만들기까지 남는다 — 실측을 보고 압축이 필요한지 정한다. |
| Q7-2 | BOM 이 붙은 파일은 첫 줄을 못 읽고, 다시 쓸 때마다 BOM 이 따라간다. CRLF 는 문제없다 | **수용** | `read_capped` 가 맨 앞 BOM 을 벗긴다. 시험 `a_bom_does_not_hide_the_first_line`(BOM + CRLF). |
| Q7-3 | `census_name` 의 `lock().unwrap()` — 한 번 오염되면 판정마다 죽는다 | **수용** | `unwrap_or_else(into_inner)` 로. |
| Q7-4 | 판정 오류 뒤 엔진이 직접 전체를 읽는 동안 미리 만들던 스레드도 돌아 두 벌이 잡힌다 | **반박(일부만 맞음)** | 미리 만드는 중에는 엔진이 판정을 건너뛴다(부록 E 1239~1251줄: `Empty` → `world.prebuild = Some(job)` → `true`). 스레드가 끝나야 엔진이 직접 읽으므로 두 벌이 겹치지 않는다. 겹치는 것은 180초 시간 초과 뒤뿐이고, 이는 별도 Claude 가 이미 적은 것(지적 7의 둘째 줄). 취소 표시를 넣는 일은 미룬다. |
| Q8-a | 새 줄 하나가 상한보다 크면 그대로 저장된다 | **반박** | 한 줄의 크기는 `Entry::of` 가 막는다. 다만 Q8-b 로 더 줄였다. |
| Q8-b | 400"자" 상한이라 한글이면 한 줄이 수십 KB — 기록 4~5건에 상한이 찬다 | **수용** | 구역 id 는 40자로(`MAX_SECTION_CHARS`). 한 줄 최대 약 52 KB → 약 12 KB. |
| Q8-c | 센 값의 `max_ms` 가 재시작 전까지 남는다 | **기록만** | 진단은 `last_ms`/`avg_ms` 로 읽는다. |
| Q8-d | `parse_cpu_sets`: 낯선 종류의 짧은 항목(19바이트 미만)을 만나면 뒤의 코어 목록까지 못 읽는다 | **수용** | 머리 8바이트만 먼저 보고, 길이 19 검사는 종류 0 안에서. 시험에 16바이트 낯선 항목 추가. |

## 이번 방식에 대한 평가

- 수용 7 / 기록 3 / 반박 5. 55차(수용 2 / 14)와 견주면 쓸모 있는 지적의 비율이 크게 올랐다.
- **Gemini 만 찾은 것**: Windows 의 이름 바꾸기 거부(Q1-a), 접합을 따라가는 쓰기(Q2), 15.6ms 분해능(Q5), BOM(Q7-2), 죽은 칸의 글자 버퍼(Q7-1). 모두 "Linux 에서만 돌렸다"는 공통 약점 쪽이었다.
- **반박한 것의 까닭**: 대부분 부록에 없는 코드(단일 실행 플러그인, 수집기의 `Rel` 열거형)를 몰라서였다. 다음 의뢰서는 "부록 밖에서 이 코드를 지키는 장치"를 한 줄씩 적어 준다.
