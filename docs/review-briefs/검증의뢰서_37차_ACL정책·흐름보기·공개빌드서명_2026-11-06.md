## 2. 질문 (공격자 관점 먼저)

**Q1 (ACL weight 와 다른 정책의 상호작용 — 작성 중 결함 발견·수정)**: 끊기·첫 실행 관찰 차단은 weight 를 FWP_EMPTY(BFE 자동, [0, 2^60) — Microsoft Learn "Filter Weight Assignment")로 두었고 ACL 은 ≈2^63 명시 weight 라, ACL "모든 상대 · 허용" 한 줄이 끊기 차단을 이겼다. 수정: 번호 없는 차단은 FWP_UINT8 범위 식별자 14([14·2^60, 15·2^60), 하위 60비트 자동), process_not 허용 0xF000…, ACL 은 0x8000… 아래(러너 단언 "unnumbered security block beats ACL allow #1" 추가). 남은 질문: ① process_not 예외 허용(구간 15)이 ACL 차단보다 위라, 다른 정책의 예외가 ACL 차단을 뚫는 순서 ② 이미 설치된 PC 의 옛 필터(FWP_EMPTY 로 들어간 것)는 재적용 전까지 낮은 구간에 남는다 — 업그레이드 때 다시 거는 것으로 충분한가 ③ 다른 공급자(타사 방화벽)의 Sublayer 와의 중재는 우리 weight 와 무관 — 우리가 놓치는 것.

**Q2 (인터페이스 별칭)**: 정책에는 별칭을 저장하고 적용 때 LUID 로 바꾼다. 공격자(관리자 아님)가 같은 별칭의 인터페이스를 만들거나(VPN 어댑터 설치) 별칭을 바꿔 규칙이 엉뚱한 인터페이스에 걸리거나 빠지게 하는 순서. 재부팅·어댑터 재설치 뒤 LUID 가 바뀌었을 때 서비스 재시작 대조가 옛 LUID 필터를 남기는 문제.

**Q3 (ICMPv4 차단)**: ALE_AUTH_CONNECT/RECV_ACCEPT 에서 ICMP 를 막을 때 경로 MTU 탐색(ICMP type 3 code 4)·오류 메시지가 함께 막혀 TCP 가 멈추는 경우가 있는가(추측: ALE 는 echo 같은 새 흐름만 본다). 막아도 안전한 범위를 문서 근거로.

**Q4 (일회용 서명 키)**: 릴리스 키를 버리므로 판을 올릴 때 서비스와 UI 를 같은 설치 프로그램이 함께 바꾼다. 업그레이드 도중(서비스는 새 판, UI 는 옛 판) 인증이 끊기는 순서, 공격자가 옛 판 서명 UI(지문 다름)를 설치 폴더에 넣을 수 없는지(관리자 전용 폴더 전제), 다운그레이드 공격(옛 판 설치 파일 재실행)으로 알려진 결함 판으로 되돌리는 순서.

**Q5 (ACL 표 원문 되읽기)**: 화면은 서비스가 돌려준 ACL 원문(YAML)을 정규식으로 다시 표로 읽는다. 고급 편집기로 손으로 쓴 ACL(같은 이름 "ACL" 기록)이 표로 잘못 읽혀, 사용자가 본 표와 실제 걸린 규칙이 다른 순서가 있는가.
