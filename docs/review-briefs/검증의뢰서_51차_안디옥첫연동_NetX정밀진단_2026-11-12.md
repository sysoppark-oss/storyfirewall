# 검증의뢰서 51차 — 안디옥 첫 연동: 사건 카드의 [NetX로 정밀 진단] (2026-11-12)

기준: 통합프로젝트 「안디옥 플랫폼 설계와 에피스틀 규격 (0.15판 초안)」 8.1 "첫 연동", 8.3, 6.3, 6.7 (기획자 확정 2026-11-12).
범위: 스토리방화벽 **설치 프로그램과 화면만**. 서비스(관리자 권한)는 바꾸지 않았다.

## 1. 구현한 것

1. **설치 프로그램**(`ui/src-tauri/installer-hooks.nsh`): 설치·업그레이드 뒤 `HKLM\SOFTWARE\Antioch\Modules\storyfirewall`에
   `Exe`(서비스 실행 파일), `ClientExe`(화면 실행 파일), `Kind=service`, `Api=1.0`을 쓴다. 제거할 때 이 열쇠만 지운다
   (위의 `Modules`, `Antioch` 열쇠는 다른 프로그램·언어 설정이 함께 쓰므로 건드리지 않는다). 업그레이드가 부르는 이전 판 제거(/UPDATE)는 지우지 않는다.
2. **화면 코어**(`ui/src-tauri/src/rack.rs`, 일반 권한): 명령 둘.
   - `netx_registered`: `HKLM\...\Modules\netx`의 `Exe` 값이 있으면 참 → 사건 카드에 단추를 보인다.
   - `netx_diagnose(ip, port)`: 아래 순서. 하나라도 어긋나면 **한 글자도 보내지 않고** 끝낸다.
     1) `ip`를 IP 주소로 해석(안 되면 끝). 2) HKLM의 NetX `Exe` → 운영체제의 최종 경로(`GetFinalPathNameByHandle`)
     → Program Files(`SHGetKnownFolderPath`로 얻은 두 폴더) 아래인지. 3) `HKCU\SOFTWARE\Antioch\Running\netx`의 `PipeName`이
     `\\.\pipe\netx-<hex 32자>` 형식인지(없거나 다르면 "NetX를 먼저 켜 주세요"). 4) 파이프를 연다(SQOS 식별 수준).
     5) `GetNamedPipeServerProcessId` → `OpenProcess`로 핸들을 잡고 `QueryFullProcessImageName` → 최종 경로가 2)의 경로와 같은지.
     6) `rack.hello`(module=netx, api 메이저 1, granted에 operate) → 7) `rack.handoff`.
3. **보내는 값**: `{request_id, intent:"diagnose.target", from:"storyfirewall", entities:[{type:"endpoint", ip, port}]}` 뿐.
   `note`(사건 번호), `proto`, 도메인, 경로, 본문은 싣지 않는다.
4. **화면**(`ui/src/netx.ts`, `story.ts`): 카드의 접속지가 IP면 그것을 넘긴다. 도메인 이름이면 이름은 보내지 않고,
   기존 조회 `cut.preview`가 주는 이 사건의 접속 주소 목록에서 사용자가 한 곳을 고른다(최대 8곳).
   결과는 "…— NetX로 넘겼습니다. 진단 실행은 NetX에서 직접 누르세요" 한 줄.
5. **순수 함수 크레이트** `crates/rack`: 파이프 이름 형식, 경로 정규화·비교, Program Files 아래 판정, hello·handoff 메시지와 응답 검사.
   Linux 단위 시험 8건. 설치 시험(A28)에 등록부 값 확인과 제거 뒤 삭제 확인을 넣었다.

## 2. 먼저 묻는 것 — 이 설계가 깨지는 입력·순서를 적어 달라 (공격자 관점)

- Q1. 일반 권한 악성코드가 `HKCU\...\Running\netx\PipeName`을 자기 파이프로 바꿔 놓았다. 5)의 "서버 프로세스 실행 파일 = 등록된 Exe" 확인을
  통과하거나, 확인 **전에** 우리 쪽에서 무엇인가 새어 나가게 할 방법이 있는가? (예: 진짜 NetX 프로세스 안에서 파이프를 열게 하는 방법,
  서버 PID가 가리키는 프로세스를 바꿔치기하는 순서, 접속만으로 얻는 정보)
- Q2. 5)에서 `GetNamedPipeServerProcessId`가 준 PID로 `OpenProcess`하기까지의 틈. 파이프 핸들을 쥐고 있는 동안 서버 프로세스가 끝나고
  같은 PID가 재사용되는 순서가 실제로 가능한가? 가능하다면 더 안전한 확인 순서는?
- Q3. 2)의 "Program Files 아래" 판정을 속이는 경로(정션·심볼릭 링크·하드 링크·대체 데이터 스트림·8.3 짧은 이름·`\\?\` 변형·다른 볼륨 마운트).
  최종 경로로 바꾼 뒤 비교하는 것으로 충분한가? Program Files 아래에 일반 사용자가 쓸 수 있는 하위 폴더가 있는 설치(잘못된 ACL)는 어떻게 다뤄야 하나?
- Q4. 보내는 값이 주소·포트뿐이어도 새는 것이 있는가? (예: `request_id`, 누른 시각, 어느 사건에서 눌렀는지를 NetX 쪽에서 추정)
  접속지가 사설 주소·루프백·링크 로컬일 때 넘기면 안 되는 경우가 있는가?
- Q5. 도메인 사건에서 `cut.preview`의 주소 목록을 후보로 쓰는 것: 그 목록에는 사건의 다른 프로그램이 접속한 주소도 섞인다.
  사용자가 엉뚱한 주소를 넘기게 되는 경우와, 더 나은 후보 선정 방법(서비스를 바꾸지 않는 범위에서).
- Q6. 설치 훅: 32비트/64비트 등록부 보기(WOW6432Node)에 잘못 쓰일 조건, 업그레이드·제거·재설치 순서에서 값이 남거나 빠지는 경우,
  설치 폴더를 바꿔 설치한 경우.

## 3. 결정 사항

- 첫 판은 NetX를 대신 실행하지 않는다. 꺼져 있으면 "NetX를 먼저 켜 주세요"만.
- 단추는 NetX가 등록돼 있을 때만 보인다(앱을 켠 동안 한 번 확인).
- 응답의 오류 문구(NetX가 보낸 글자열)는 제어 문자를 빼고 120자로 잘라 글자로만 표시한다.

## 4. 미결 사항

- 실기 확인: NetX 쪽 입구(bridge/)가 이 판의 등록부·메시지와 실제로 맞물리는지는 NetX가 PC 전체 설치로 등록된 뒤에 확인한다.
- 서비스가 NetX 등 다른 구성원을 받는 쪽(rack.* 메서드, 8.1 표의 나머지)은 이번 범위가 아니다.
- UI 명세에 이 단추의 자리(보조 단추 맨 왼쪽)를 다음 판에 적는다.
