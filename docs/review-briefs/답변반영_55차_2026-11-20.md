# 답변반영 55차 — 전체 판정 미리 만들기·보관 정리 색인·진단 기록 (2026-11-20)

의뢰서: 검증의뢰서_55차_전체판정미리만들기_2026-11-20.md · Gemini 는 저장소를 열지 못해(raw.githubusercontent.com 차단) 문서와 공식 명세만으로 답했다. 추측 부분은 코드로 하나씩 확인했다.

| 번호 | Gemini 지적 | 판단 | 근거·조치 |
|---|---|---|---|
| Q1-a | `prebuild_off` 가 한 번 실패로 영영 꺼진다 → 디스크를 바쁘게 해 180초를 넘기면 "엔진 12~15초 막힘"이 되살아난다 | **수용** | 맞다. `runtime.rs` 세 곳에서 `prebuild_off = true` 뒤 되돌리는 길이 없었다. `prebuild_off_until` + `PREBUILD_RETRY_AFTER`(2시간)로 바꿈. 시험 `prebuild_backoff_ends_after_retry_window`. |
| Q1-b | 만드는 중에도 고위험 사건이면 판정을 깨우기 | **반박(지금은)** | 만드는 중에 판정하면 변경 기록을 지워(`pruned`) 미리 만든 것을 못 받는다(`adopt` ④). 깨우려면 "지우지 않는 판정"이 따로 있어야 한다 — 54차 Q1(판정을 엔진 밖으로)과 한 묶음으로 미룬다. 차단(WFP)은 판정과 무관하게 실시간이다. |
| Q1-c | 창이 열린 때를 밖에서 알아챌 수 있다 | **수용(고치지 않음)** | 로컬 사용자 권한이면 CPU·디스크로 짐작할 수 있다. 숨길 방법이 없고, 창은 18~33초·상한 180초다. 한계로 적는다. |
| Q2-ⓐ | 뷰와 뿌리를 한 트랜잭션에서 읽는가 | **검증: 문제 없음** | `incremental.rs` `build()` 가 `ReadTx::begin` 안에서 스키마 판·`last_seq`·`MAX(id)`·`View::load` 를 모두 읽고 닫는다. 뿌리는 그 뷰에서 계산한다(DB 를 다시 읽지 않음). |
| Q2-ⓑ | 받은 뒤 '*' 를 만나면 | **검증: 알려진 동작** | `run` 이 `None` 을 돌려 엔진이 직접 전체를 읽는다(틀린 결과는 아님, 그때만 엔진 12~15초). '*' 는 보관 정리만 남기는데 ⓒ 로 이미 무효가 된다. |
| Q2-ⓒ | 만드는 중에 보관 정리가 시작되면 지워진 선을 품은 결과를 받는다 | **반박** | `run_retention` 의 `can_prebuild` 에 `world.prebuild.is_none()` 이 있다. 만드는 중이면 `request_full` 로 가지 않고 `invalidate()` → `epoch + 1` → 만들던 것은 `adopt` ①에서 버려진다. Gemini 가 제안한 고침과 같은 동작이 이미 있다. |
| Q2-ⓓ | epoch 가 토글·좁은 정수면 ABA | **반박** | `epoch: u64`, `invalidate` 마다 `+= 1` 뿐이다. |
| Q3 | 보관 정리 뒤 18~33초 동안 지워진 선을 가리키는 화면·끊기 | **검증: 새 문제 아님, 조치 없음** | 바꾸기 전에도 `drop_judged()` 가 결과를 `judged_prev` 로 옮겨 새 판정까지 직전 것을 보여 줬다(같은 뜻). 지워진 선을 열면 `StoryExplain` 은 `edges_visible` 에서 걸려 범위 밖 오류를 돌려준다(근거 없는 문장을 만들지 않는다). 사건에 속한 선(장 있음)은 30일 보관이라 그 창에 지워지는 것은 30일 지난 사건뿐이다. |
| Q4 | "사건 아님"·접기가 DB 의 장을 바꾸면 `written` 과 어긋난다 | **반박** | 장을 쓰는 곳은 판정 한 곳뿐이다(`judge/src/lib.rs` `UPDATE edges SET chapter = ?1 WHERE id = ?2 AND chapter IS NOT ?1`). 접기는 장 없는 선을 지울 뿐 장을 바꾸지 않고, "사건 아님"은 장을 건드리지 않는다. 만드는 동안 판정은 쉰다. |
| Q5-a | `INDEXED BY` 는 조건이 어긋나면 오류 → 보관 정리 통째 실패 | **반박(빼지 않음)** | 사실은 맞다. 다만 빼면 계획기가 다른 색인을 골라 20초로 돌아갈 수 있다(넣은 이유). 조건이 어긋나면 `graph` 보관 정리 시험이 그 SQL 을 실제로 돌리므로 CI 에서 먼저 깨진다. |
| Q5-b | 옛 DB 에서 색인을 처음 만들 때 엔진이 막힌다 | **수용(기록)** | 한 번뿐이고 노트북(1.1 GB)에서는 이미 지나갔다. 시간을 재 두지 않았다 — 다음에 색인을 더할 때는 시작 기록에 걸린 시간을 남긴다. |
| Q5-c | 장 없는 사건 선의 근거가 지워진다 | **검증: 이번 변경과 무관** | 모으는 집합의 정의("장 있는 선의 근거 + edge_evidence")는 바꾸기 전과 같다(edf2810 은 출발점만 바꿨다). 사건 사슬의 선에는 판정이 장을 쓴다. "장 없이 사슬에 든 선이 있는가"는 따로 확인할 거리로 남긴다. |
| Q6 | 64개 넘는 프로세서·ARM64·가상 머신에서 클럭 값이 틀린다 | **수용(기록만)** | 버퍼는 충분하고 실패해도 그 값만 빠진다. 진단용 평균이라 그룹 하나만 보여도 판정에는 영향이 없다. 가상 머신에서 현재=최대로 고정되는 것은 한계로 적는다. `GetLogicalProcessorInformationEx` 로 바꾸지는 않는다. |
| Q7 | 커널/사용자 시간 분리, 프로세서 번호, 페이지 폴트 | **수용** | `crates/svc/src/perfdiag.rs`: 커널 CPU 시간, 페이지 폴트 차이, 지금 코어의 효율 등급(`GetSystemCpuSetInformation` 의 EfficiencyClass + `GetCurrentProcessorNumberEx`). 번호 대신 등급을 남긴다 — 어느 번호가 효율 코어인지 따로 알 필요가 없다. 시험 3건. |
| 추가 | `from_ts` 가 15초마다 전진하면 받을 때마다 범위가 달라 끝없이 다시 만든다 | **반박** | `from = world.last_judge_ts` 는 0 으로 두고 바꾸지 않는다(창 하한이 움직이지 않는다). 실측에서도 "받음"으로 끝난다. |

## 남긴 것

- 판정을 엔진 밖으로 옮기기 + 만드는 중에도 깨우기(54차 Q1, 55차 Q1-b).
- 장 없이 사건 사슬에 든 선이 있는지(Q5-c).
- 색인을 새로 만들 때 걸린 시간 기록(Q5-b).
